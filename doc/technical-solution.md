# 个人技术实践门户技术方案

## 1. 文档目标

本文为个人技术实践门户定义首期产品边界、系统结构、数据模型方向和演进路径。当前已有 React 前端 MVP，后端尚未实现；后端技术基线调整为 Node.js、TypeScript、Fastify 和 MongoDB。

## 2. 产品目标与范围

门户聚合个人技术学习与实践内容，并逐步扩展为交流社区。

### 首期目标

- 访客可浏览个人介绍、学习笔记和项目实践。
- 内容可按分类和标签浏览，并支持站内搜索。
- 站点所有者可登录、创建和维护内容。
- 页面具备稳定、可分享的 URL 和基础 SEO 元信息。

### 后续目标

- 注册用户可在论坛发帖、回复和举报内容。
- 管理员可管理用户、分类、内容和举报。
- 根据实际流量与协作需求，逐步增加通知、关注、收藏等功能。

首期不建设独立微服务，也不把复杂社交功能作为上线前置条件。

## 3. 信息架构

| 区域 | 主要能力 | 建议路由 |
| --- | --- | --- |
| 首页 | 个人简介、精选内容、近期更新、项目入口 | `/` |
| 学习笔记 | 列表、详情、分类、标签、目录、相关文章 | `/notes`、`/notes/[slug]` |
| 项目实践 | 项目列表与详情、技术栈、实践记录、演示和代码链接 | `/projects`、`/projects/[slug]` |
| 交流论坛 | 分类/话题、帖子、回复、举报 | `/forum`、`/forum/[slug]` |
| 关于 | 个人经历、联系方式、站点说明 | `/about` |
| 管理端 | 内容编辑发布、项目维护、论坛管理 | `/admin` |

公开页面和管理页面属于同一前端应用，但应使用独立布局；管理操作的访问控制由后端统一校验。路由中的 `slug` 应稳定且唯一；内容标题修改不应自动改变已发布 URL。

## 4. 总体架构

### 4.1 架构决策

首期采用**前后端分离的模块化单体**：React 前端通过 HTTP/JSON API 访问一个 Node.js + TypeScript + Fastify 后端；后端按业务域隔离模块，使用 MongoDB 保存业务数据。这样可简化部署，同时保留未来拆分论坛或搜索的边界。首期不单独引入 Redis、消息队列或微服务。

```text
浏览器
  └── React + TypeScript 前端（公开站点 / 管理端）
        └── HTTP/JSON API
              └── Node.js + TypeScript + Fastify 后端（模块化单体）
                    ├── 内容模块（笔记、分类、标签、媒体）
                    ├── 项目模块（项目与实践记录）
                    ├── 身份与权限模块
                    ├── 论坛模块（后续阶段）
                    └── 搜索模块
                          ├── MongoDB（业务文档、索引和首期搜索）
                          └── 对象存储（图片等媒体文件）
```

后端模块通过明确的服务接口协作，避免跨模块直接访问内部实现。MongoDB 集合按业务边界组织；文档间仅在数据通常一起读取且有界时嵌入，可能持续增长或需要独立分页的内容单独存储并通过 ObjectId 关联。首期无需消息队列或独立搜索服务。

### 4.2 技术基线

| 层次 | 建议 | 用途 |
| --- | --- | --- |
| 前端 | TypeScript + React | 公开站点和管理端；路由、构建工具及 UI 组件库在初始化时确定 |
| 后端 | Node.js + TypeScript + Fastify | 提供业务 API、认证授权及业务模块 |
| API | HTTP/JSON REST API | 前后端交互；统一分页、校验和错误响应格式 |
| 文档数据库 | MongoDB | 内容、用户、论坛数据；通过集合、文档和索引支持访问模式 |
| 数据访问与迁移 | MongoDB Node.js Driver、版本化迁移脚本 | 类型化数据访问；显式维护索引及需要的 MongoDB schema validator |
| 内容格式 | Markdown | 便于编写和迁移；渲染时禁用不安全 HTML 或进行净化 |
| 媒体 | S3 兼容对象存储 | 保存图片等文件；数据库只保存文件元数据和对象键 |
| 部署 | 前端静态托管/CDN，后端 Node.js 容器或托管服务 | 与 MongoDB 和对象存储按环境配置连接 |

Fastify 路由应使用 JSON Schema 定义请求校验和响应结构，并通过插件封装认证、数据库连接和业务能力。认证采用服务端可撤销的安全会话 Cookie，生产环境结合 HTTPS、CSRF 防护和严格 Cookie 属性；具体插件在后端初始化时确认。首期只开放站点所有者账号；论坛开放注册前，应确认邮箱验证、找回账号和垃圾内容处理方案。

## 5. 业务模块与边界

### 5.1 内容模块

负责笔记、分类、标签、草稿、发布状态和公开内容查询。笔记正文保存为 Markdown 文本；标题、摘要、slug、作者、发布时间等作为文档字段保存。分类和标签通过 ID 引用，便于独立维护；渲染层统一处理 Markdown 扩展、代码高亮、目录生成和链接安全。

### 5.2 项目模块

负责项目介绍及其实践记录。项目文档保存名称、slug、摘要、说明、技术栈、代码/演示链接、封面和展示状态；实践记录作为独立集合并关联项目，避免项目更新记录形成无界数组。项目与笔记可共享标签、媒体能力，但不合并为单一的“万能内容”集合。

### 5.3 身份与权限模块

首期管理员账号通过部署环境配置邮箱和 scrypt 密码哈希；登录后使用服务端会话进行授权。论坛开放注册后再引入完整用户身份、会话和授权能力。建议角色：

- `admin`：管理用户、内容、分类、论坛和举报。
- `member`：论坛开放后可发帖、回复和举报。
- `visitor`：无需登录浏览公开内容。

授权必须在服务端执行，不能仅依靠隐藏管理入口或客户端路由判断。

### 5.4 论坛模块（后续）

论坛采用独立的分类、主题帖、回复和举报集合。设计上不将帖子与笔记混存；回复使用独立集合并关联主题帖，避免帖子文档无界增长，以便后续单独调整审核、分页、通知或部署策略。首版论坛建议开启登录后发帖，并为新账号或敏感操作保留审核能力。

### 5.5 搜索模块

首期使用 MongoDB 文本索引支持笔记和项目的基础搜索；由于文本索引建在各自集合上，搜索模块分别查询并合并、排序和分页结果。论坛启用后再决定是否纳入统一搜索。若中文分词、相关性排序或搜索规模超出文本索引能力，再评估 MongoDB Atlas Search 或独立搜索服务。

## 6. 数据模型建议

以下为逻辑集合及文档方向，具体 BSON 类型、字段约束和索引以版本化迁移脚本为准。主键使用 MongoDB `ObjectId`；跨集合引用保存为对应集合的 ObjectId：

| 实体 | 关键字段/关系 |
| --- | --- |
| `users` | `_id`、规范化后的 `email`、`displayName`、`role`、`status`、`createdAt` |
| `notes` | `_id`、`title`、`slug`、`summary`、`bodyMarkdown`、`status`、`publishedAt`、`authorId`、`categoryId`、`tagIds`、`featured`、`readingTimeMinutes`、`createdAt`、`updatedAt`、`deletedAt` |
| `projects` | `_id`、`name`、`slug`、`summary`、`description`、`techStack`、`repositoryUrl`、`demoUrl`、`categoryId`、`projectStatus`、`featured`、`status`、`publishedAt`、`createdAt`、`updatedAt`、`deletedAt` |
| `projectLogs` | `_id`、`projectId`、`title`、`bodyMarkdown`、`publishedAt` |
| `categories` | `_id`、`name`、`slug`、`parentId`（可选） |
| `tags` | `_id`、`name`、`slug` |
| `mediaAssets` | `_id`、`objectKey`、`mimeType`、`size`、`altText`、`ownerId` |
| `adminSessions` | `_id`、`tokenHash`、`expiresAt`；仅保存管理员会话令牌哈希，并通过 TTL 索引过期清理 |
| `forumTopics`（后续） | `_id`、`categoryId`、`authorId`、`title`、`body`、`status`、`createdAt` |
| `forumReplies`（后续） | `_id`、`topicId`、`authorId`、`body`、`status`、`createdAt` |
| `reports`（后续） | `_id`、`reporterId`、`targetType`、`targetId`、`reason`、`status` |

为 `users.email`、`notes.slug`、`projects.slug` 等字段建立唯一索引；公开列表建立按状态、发布时间和 `_id` 排序的复合索引，并按实际筛选方式为 `categoryId`、`tagIds` 建立索引。会话集合按过期时间建立 TTL 索引。文本索引覆盖各集合所需的标题、摘要和正文/描述字段。所有公开内容都需要明确的发布状态和发布时间；公开查询只返回已发布内容。删除策略按业务需要选择，避免无依据地为所有集合增加复杂审计设计。

## 7. 关键交互与接口约定

- 公开页面通过前端调用只读 API 获取数据；按 SEO 与分享预览要求选择支持 SSR/SSG 的 React 方案或预渲染方式，并设置合适的缓存策略。
- 笔记列表/详情使用 `GET /api/v1/notes`、`GET /api/v1/notes/:slug`；列表支持分页、分类/标签、关键词和精选筛选。
- 项目列表/详情使用 `GET /api/v1/projects`、`GET /api/v1/projects/:slug`；列表支持分页、分类、技术栈、项目状态、关键词和精选筛选。
- 管理会话使用 `POST /api/v1/admin/session` 登录、`GET` 查询、`DELETE` 登出。
- 管理笔记使用 `GET/POST /api/v1/admin/notes`、`GET/PATCH/DELETE /api/v1/admin/notes/:slug` 和 `POST` 发布/撤销发布；新建为草稿，删除采用软删除。
- 管理项目使用 `GET/POST /api/v1/admin/projects`、`GET/PATCH/DELETE /api/v1/admin/projects/:slug`；登记后直接公开，删除采用软删除。
- 管理端写操作必须验证会话、角色和输入数据；Markdown、URL、上传文件均需做相应校验。
- 列表接口支持分页、分类/标签筛选和稳定排序；避免一次返回全部内容。
- 错误响应保持统一结构，区分未登录、无权限、校验失败和资源不存在。
- slug 通过 MongoDB 唯一索引保证唯一。改名且需要保留旧链接时，使用显式重定向集合记录。
- 索引和文档校验规则通过版本化迁移脚本维护；生产环境不得在应用启动时静默创建/修改结构，迁移应作为发布步骤显式执行。
- 列表查询使用有上限的分页和稳定排序；数据量增长后优先使用基于索引的游标分页，避免大 `skip`。

## 8. 安全、可靠性与运维

- 管理员凭据由环境变量配置，密码使用 scrypt 哈希；会话令牌随机生成，仅存其 SHA-256 哈希。会话 Cookie 设置 `HttpOnly`、合适的 `SameSite`，生产环境启用 `Secure`。
- 管理写请求必须通过服务端会话校验和 `ADMIN_ORIGIN` 来源校验；生产环境使用 HTTPS，并在部署入口限制登录尝试。
- Markdown 渲染禁止未经净化的原始 HTML，外链和嵌入内容按允许策略处理。
- 数据库凭据、认证密钥和对象存储密钥通过部署环境的密钥管理注入，不提交到仓库。
- 生产环境配置 MongoDB 数据备份，并定期验证恢复流程；索引或校验规则变更前确认回滚/恢复方案。
- 记录服务端错误和管理操作所需的最小审计信息；日志中避免保存密码、会话令牌等敏感数据。
- 论坛开放后增加举报处理、用户封禁、内容隐藏和垃圾内容限流机制。

## 9. 部署形态

前端作为静态资源部署到托管平台或 CDN，后端以 Node.js 服务部署，并连接 MongoDB（可采用 MongoDB Atlas）和对象存储。环境至少区分本地开发、预发布和生产；各环境使用独立配置与数据。生产发布步骤包括运行兼容的数据库迁移脚本、部署应用和验证关键页面。应用复用 MongoDB 连接池，并对连接 URI、超时和池大小按部署环境配置。公开静态资源可利用 CDN 缓存；管理接口和个性化页面不得被公共缓存误缓存。

## 10. 实施阶段

### 阶段一：门户 MVP

- 初始化 Node.js + TypeScript + Fastify 后端，配置 MongoDB 连接和环境变量管理。
- 定义 REST API 并实现公开内容查询，逐步将前端从本地演示数据接入后端。
- 完成首页、关于、笔记和项目公开页面。
- 实现分类、标签、分页、Markdown 渲染和基础搜索。
- 通过种子数据或受控管理流程维护首批内容。

### 阶段二：内容管理

- 增加管理员登录、草稿/发布流程、预览和媒体上传。
- 加入输入校验、服务端权限检查和基础 SEO 元信息。
- 建立迁移、备份和部署验证流程。

### 阶段三：论坛基础版

- 增加注册/登录、论坛分类、帖子、回复和举报。
- 实现管理员审核、用户封禁、分页和基本限流。
- 根据实际运营情况逐步开放新用户发帖权限。

### 阶段四：按需增强

- 基于用户反馈增加通知、收藏、关注等功能。
- 当性能、团队协作或独立发布需求成为真实问题时，再拆分搜索或论坛服务。

## 11. 首期验收标准

- 访客可以通过桌面和移动端访问首页、笔记和项目详情。
- 已发布内容可通过稳定 URL 访问；草稿不会出现在公开列表或搜索中。
- 分类、标签、分页和搜索可组合使用，搜索结果可回到对应详情页。
- 管理写操作未登录或权限不足时会在服务端被拒绝。
- Markdown 和上传内容经过安全处理，迁移与生产配置不依赖本地开发数据。
- 站点可通过部署说明在目标环境启动，并有 MongoDB 备份与恢复方案。
